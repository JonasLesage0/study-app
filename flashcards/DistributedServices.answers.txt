🌍 From Monolith to Distributed Services
1. Why Distribute?
Concrete signals include a module becoming a scaling hotspot (consuming excessive CPU, RAM, or database resources) or change coordination slowing delivery due to team collisions. Distribution provides independent deployment and isolated failure domains, but it does not solve poor internal structure. Without cohesive modules, you simply create "Distributed Spaghetti" or a "Distributed Big Ball of Mud" with endless network chatter.
2. Spectrum Trade-offs
Architectural styles exist on a spectrum: the Monolith is a single deployable unit and codebase sharing the same memory space and data model, while the Modular Monolith introduces strong internal boundaries (bounded contexts as separate modules) and shared ACID transactions (all or nothing, the database is always valid). SOA involves distributed services that often still share data models. At the far end, Microservices are domain-partitioned services prioritizing autonomy through strict Database-per-Service ownership. Operational complexity rises fastest for Microservices because reliable in-process function calls are replaced by unreliable network hops, necessitating mature DevOps and service orchestration. Additionally, because global ACID is impossible across separate databases, microservices must use Sagas: a sequence of local transactions coordinated via events where Compensating Actions ("undo" logic) are required to reach eventual consistency if a step fails (e.g., partial network failures).
3. Distributed Fallacies in Practice
Three fallacies that can break workflows like subscription or payment expiration: "The network is reliable": An integration event like PaymentExpired might be sent but never received by the Accounts service due to a transient network failure, resulting in a user keeping premium access despite an expired payment. "Latency is zero": If a UI synchronously waits for confirmations from multiple services during a subscription update, network hops add cumulative delay, potentially causing timeouts that break the user experience. "There is only one administrator": In a distributed system, no single person has a global view or the ability to manually fix data inconsistencies between the Payments and Accounts databases easily, leading to "eventual consistency" headaches during troubleshooting.
4. Bounded Context + Runtime
Defining microservices as "Bounded Context + Distributed Runtime" is more precise than "small services" because size is subjective and irrelevant to the core goals of the architecture. This definition emphasizes that a microservice is the physical embodiment of a semantic boundary. Each service must own its own code, its own data, and its own deployment to achieve true autonomy, ensuring that when one bounded context (like Accounts) changes, others (like Taskly) do not have to stop and wait.
🧱 Boundaries, Granularity, and Data
5. Goldilocks Granularity
Too Small (Nano-services): Symptoms include endless network chatter, complex event chains that are hard to trace, and high overhead for managing many tiny deployment units. Too Large: The primary symptom is a distributed monolith, where services are logically coupled such that they cannot be deployed independently. Just Right: Finding the balance requires workflow alignment. Tracing a real business workflow, such as "Create subscription," reveals if a service boundary is correct; if that single action requires data from five different services, those services are likely split by entities rather than transaction boundaries and should perhaps be merged.
6. Distributed Monolith Smells
Evidence includes lockstep deploys (releasing multiple services at once), intimate knowledge of the internals of other services, and schema changes in one service forcing immediate code changes and deployments in others. This results in a system that has the operational cost of distribution without the benefit of autonomy.
7. Database-per-Service Rule
A shared integration database is a trap because it destroys change control and breaks Bounded Context boundaries. It introduces schema coupling, where Service A (e.g., Accounts) renames a column and Service B (e.g., Taskly) immediately crashes because it was reading from the same table. This coupling turns every database adjustment into a cross-team release coordination nightmare.
🔄 Workflows, Contracts, and Reliability
8. Sagas and Transaction Boundaries
Distributed systems use Sagas because splitting databases makes ACID (Atomicity, consistency, Isolation, Durability) transactions (all or nothing, the database is always valid, instant consistency) across services impossible; each service can only commit its own data locally. A Saga is a sequence of local transactions coordinated through events. Compensating actions are crucial; they are triggered if a later step in the sequence fails, reversing or neutralizing the effects of previous successful steps to maintain eventual consistency.
9. Contract Taxonomy
Domain Events express something that happened inside a bounded context (e.g., UserSubscribed), and are primarily for internal consistency and local side-effects. Integration Events express something other bounded contexts can rely on, and serve as stable Public API contracts for cross-service collaboration. Only integration events should cross boundaries to protect the Anti-Corruption Layer (ACL). Serializing internal domain entities directly creates tight semantic coupling, where a refactoring (in the core) would break all downstream (external) consumers, destroying service autonomy.
10. Contract Evolution
Contracts are "build inputs" because modern tooling (like AsyncAPI in Taskly) uses them to generate routing logic and controller resolutions at runtime, making them active parts of the system's execution rather than just static documentation. The expand-and-contract versioning pattern reduces breaking changes by first adding new fields to a contract (expand) and only removing old fields (contract) once all consumers have migrated to the new version.
11. Async Reliability Chain
These patterns form a chain to ensure "at-least-once" delivery in unreliable networks: The Transactional Outbox saves outgoing events in the same database transaction as the business data, solving the "dual-write" problem where a database save succeeds but the event fails to publish. The Relay Worker is a background process that scans the outbox and ensures events are eventually published to the broker. Inbox Deduplication is used by the consumer to track processed message IDs, preventing the same event from being handled twice (ensuring idempotency). The DLQ (Dead Letter Queue) quarantines "poison messages" that fail repeatedly, allowing the main queue to keep moving while providing a place for humans to inspect and replay failures.
