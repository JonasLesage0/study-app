Composition Root Responsibilities
1. Why Main Is Allowed to Be "Dirty"
Main acts as the Composition Root (the "5th element"). Its explicit responsibility is to wire the application together, requiring references to all layers (Application, Infrastructure, and frameworks). By concentrating this "dirty" coupling in Main, the Domain and Application layers are shielded from dependency clutter and remain entirely technology-agnostic.
2. Module Wiring Order
In AddModules(), the order is critical because the DI container builds the object graph (runtime network of objects and references) incrementally. This means a module providing a service (e.g., DomainEvent) must be registered before modules that consume it (e.g., Persistence and Messaging). If the order is incorrect, the application will fail to resolve required services during the startup phase.
3. Startup Pipeline
The pipeline starts in Program.cs (or Main.ts) with two distinct phases: Service Registration and Runtime Execution. Service registration (composition) occurs during builder.Services.AddModules(...), where the DI container builds the object graph by binding ports to adapters. Runtime execution occurs when UseModules() is called, which activates the middleware pipeline, applies database migrations, seeds data, and starts background workers.
DI, Ports, and Runtime Configuration
4. Port-to-Adapter Registration
In persistence modules (such as AddEFCoreServices), driven ports like IUnitOfWork, repositories, and queries are mapped to concrete adapters through DI registration (e.g., services.AddScoped<IUnitOfWork, EntityFrameworkUoW>()). This is the configurator's job because it's the only place where "ports meet adapters", allowing the core to remain oblivious to the specific technology being used.
5. Keyed Messaging Controllers
Controllers are registered using keyed scoping with the OperationId from the AsyncAPI specification. This enables the message processor to resolve the specific controller implementation at runtime by looking up the operation ID from the incoming message metadata.
6. Options Binding Boundary
Configuration sections (like PaymentsOptions or broker settings) are bound in the Main/Infrastructure wiring to prevent the Application layer from depending on the framework-specific IConfiguration interface, which is a technical detail that does not belong in the core. This ensures that configuration values are translated into strongly-typed application-friendly options or ports before they are injected into use cases.
7. Lifetime Decisions
Publishers and message brokers are typically registered as Singletons because they manage process infrastructure, such as persistent connections to external brokers, that should last for the entire application lifetime. Conversely, use cases, repositories, and the Unit of Work are registered as Scoped to ensure they have a fresh, isolated state and a consistent transaction boundary for each individual business operation or request. Use Transient for a new instance every time requested. Long-running listeners (e.g., ScanForExpiredPaymentsJob) typically run as hosted/background services.
8. Reflection Registration Trade-offs
Auto-registering policies via reflection creates a "boot-time convention" that automatically wires new handlers, significantly reducing manual boilerplate and the risk of forgetting to register a new policy as the system grows. However, operational risks include a "hidden" dependency graph, making it more difficult to debug why a specific registration is missing. Startup times are slower because the application must scan entire assemblies to find implementations at runtime.
9. Swapping Infrastructure Implementations
Because the core layers follow the Dependency Rule and only depend on abstract ports, swapping a persistence adapter (e.g., from EF Core to MemoryLane) only requires modifying the module registration files within Main. The Domain and Application layers remain entirely untouched because they are "blissfully ignorant" of concrete infrastructure details. This makes swapping a wiring problem in the configurator rather than a refactoring effort in the core business logic.
